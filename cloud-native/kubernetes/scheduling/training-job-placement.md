# 分布式训练作业：从成组准入到故障恢复

平台交付的是一组可用且互联的设备，训练作业交付的是可持久恢复的优化步。两者之间至少有四个不同事件：队列准入、Pod 绑定、所有 rank 会合（rendezvous）、第一次优化器更新。拿到前一个事件不能证明后一个已经发生。

## 64 张空闲卡的两种放置结果

设作业需要 8 个 worker Pod，每 Pod 在同一节点独占 8 张同型卡；没有另占名额的 launcher。先忽略 CPU、内存和网络限制。下面两种快照的空闲卡数相同：

| 空闲分布 | 可放下整组的 worker 数 | 结论 |
| --- | ---: | --- |
| 8 台各空 8 卡 | 8 | 满足节点内整组条件；仍要检查队列配额和跨节点拓扑 |
| 16 台各空 4 卡 | 0 | 单个 Pod 不能跨节点凑卡；放宽排队优先级本身不会整理碎片 |

一般地，忽略其他约束时，可容纳的同规格 worker 上界为 `Σ floor(节点空闲卡数 / 每 worker 请求卡数)`。若要求整个作业位于同一网络域，应按域分别计算，至少一个域能放下全部 worker 才可行。kubelet 的节点内拓扑对齐不替代跨机架或跨交换网络的放置。

**换到万卡容量**：设 1,250 个同型八卡节点，1,000 个满载、125 个全空、125 个各剩 4 卡。空闲总数是 `125×8 + 125×4 = 1,500`，若只看总量，会估计能启动 `floor(1500/64) = 23` 个上述作业。按整机放置实际至多 `floor(125/8) = 15` 个；此时还没扣减配额、故障节点和网络域约束。排队报表应同时展示空闲卡数与匹配目标形状的空闲节点数。

## 调度链与证据

| 关口 | 决策 | 应取得的证据 |
| --- | --- | --- |
| 准入 | 租户配额、优先级、借用/抢占策略是否允许现在开始 | 队列、申请量、准入条件和原因；不要把尚未准入算作 GPU 不足 |
| 成组与放置 | 固定 world size 的必需成员能否一起获得符合约束的节点 | Volcano PodGroup 的 `minMember` 计 Pod，不计 GPU；8 个必需 worker 时是 8，不是 64。另有必需角色则重新核算 |
| 设备分配与会合 | 设备是否可见、每个 rank 是否唯一、是否都加入期望的进程组 | Pod→node、GPU UUID、local/global rank、world size 和 rendezvous 日志；`Running` 不是完成会合 |
| 训练与通信 | 进程组是否落在预期链路、慢 rank 在等什么 | 每个组的成员、节点/GPU/NIC 映射，collective 的消息大小、起止时刻及对应的 step |

Volcano 的 gang 策略、Kueue 的队列准入与拓扑感知放置是不同机制，不是要求依次安装的组件。实际集群应先辨认谁管理队列、谁给 Pod 绑定节点。固定规模任务若仅能启动一部分，可能持卡等待；弹性任务可以采用不同门槛，但训练程序要支持 world size 和数据进度的变化。

## 把万卡容量转化为可验收的指标

1. **先回放队列。** 使用带到达时刻、租户、优先级、运行时长、节点形状和拓扑约束的一组作业，分别比较先来先服务和允许短作业回填的策略。在相同输入和容量下按作业大小与租户分别看等待 P50/P95、最大等待、可成组资源以及抢占损失。只提高平均利用率可能让大作业一直排不到。
2. **再扩大实际训练。** 从一台到两台、再到同一网络域和跨域，固定有效全局 batch 和模型。比对队列等待、会合时间、各 rank step P95、有效 token 吞吐。调度器回放不能验证网络拥塞；NCCL 微基准也不能代替端到端训练。
3. **单独验收故障恢复。** 在获准的测试作业中记录一个完整 checkpoint，再中断一个 worker。恢复时检查所有分片及完成标记、模型与优化器、学习率调度器、随机状态、数据游标和累计有效 token。对照不中断的短跑，检查恢复后下一批样本及参数更新（在约定数值容差内）。分开记录检测、重新排队、加载和重算耗时；Pod 重建不算续训成功。
